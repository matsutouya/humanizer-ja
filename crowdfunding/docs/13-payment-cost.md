# 13. 決済コストを下げる

> ⚠️ **料率はすべて「目安」。** 決済業界の料金は改定されるうえ、取引量や業種で個別に変わる。
> このドキュメントの数字は**構造を理解するための例**であって、実際は必ず最新の料金表と見積りで確認すること。
> 特に Connect の各種費用（アカウント維持・送金）は見落とされやすく、料金表を直接読むこと。

---

## 0. 先に結論

**立ち上げ期に「決済料率そのもの」を下げる手段はほぼない。** 料率交渉はボリュームが前提で、
年間流通額が数千万円に届くまで相手にされない。

だから、効くのはこの順:

| # | レバー | 効果 | 難度 | いつやる |
|---|---|---|---|---|
| 1 | **送金をまとめる**（決済ごとの自動送金をやめる） | 大 | 低 | **最初から** |
| 2 | **失敗・返金・チャージバックを減らす** | 大 | 中 | 最初から |
| 3 | **手数料の負担者を設計する**（支援者に任意負担してもらう） | 大 | 低 | 最初から |
| 4 | 決済手段のミックス（高額を低コスト手段に誘導） | 中 | 中 | Phase 6 以降 |
| 5 | PSP の料率交渉 | 大 | 高 | 流通額が出てから |
| 6 | PSP の乗り換え | 中 | **非常に高** | 基本やらない |

**1〜3 は実装コストが低いのに効果が大きい。ここから手を付ける。**

## 1. コスト構造を分解する

「決済手数料 3.6%」だけ見ていると、実際の原価を見誤る。

```
支援額 100
  │
  ├─ ① 決済手数料           約 3.6%    ← 一番目立つが、唯一のコストではない
  │
  ├─ ② Connect の構造費用    ???       ← アカウント維持費・送金ごとの費用
  │                                       ★ 見落とされやすい。取引単価が小さいと効いてくる
  │
  ├─ ③ 決済失敗による機会損失  0〜5%    ← All-or-Nothing で特に大きい
  │
  ├─ ④ 返金の実損             返金額の約3.6%  ← 決済手数料は返ってこない
  │
  ├─ ⑤ チャージバック損失      発生額 + 手数料 ← クラファンは発生率が高い業種
  │
  └─ ⑥ 付帯コスト             メール・ストレージ・監視
```

**②③④⑤ の合計は、①を上回ることが珍しくない。** 特に立ち上げ期は取引が少ないので、
固定的な費用（②）の比率が跳ね上がる。

### まず自分の原価を計算する

```ts
// lib/fees.ts に併設して、実測値から原価率を出せるようにしておく
type CostModel = {
  gmv: number                 // 流通総額
  paymentFee: number          // 実際に引かれた決済手数料（balance_transaction から集計）
  connectCost: number         // Connect 関連費用
  refundLoss: number          // 返金で回収できなかった決済手数料
  disputeLoss: number         // チャージバック損失
}

export function effectiveCostRate(c: CostModel): number {
  return (c.paymentFee + c.connectCost + c.refundLoss + c.disputeLoss) / c.gmv
}
```

**[11-payment-hardening.md](11-payment-hardening.md) の台帳があれば、この数字が正確に出る。**
`PSP_FEE_EXPENSE` / `REFUND_EXPENSE` / `DISPUTE_LOSS` を集計するだけ。台帳を入れる実利のひとつがこれ。

## 2. レバー① 送金をまとめる ★最初にやる

### 問題

destination charge で決済ごとに自動送金すると、**送金の回数だけ費用が積み上がる**。
支援1件ごとに送金が走ると、少額支援が多いプロジェクトほど不利になる。

### 対策

[11-payment-hardening.md](11-payment-hardening.md) の「送金遅延」と**まったく同じ実装で解決する。**

```ts
// 決済時: transfer_data を指定しない → 全額プラットフォーム残高へ
// 募集終了 + 7日後: プロジェクト単位で1回だけ transfer
await stripe.transfers.create({
  amount: totalPayout,          // そのプロジェクトの支援者全員分をまとめた額
  currency: 'jpy',
  destination: creator.stripeAccountId,
  transfer_group: `project_${projectId}`,
}, { idempotencyKey: `payout-${projectId}` })
```

```
【変更前】支援100件 → 送金100回
【変更後】支援100件 → 送金1回
```

**資金リスク対策とコスト削減が同じ実装で両立する。** 最も費用対効果が高い施策。

### 出品者の入金サイクルも設計する

出品者の Connect アカウントから銀行口座への入金（payout）も、回数が増えるほど費用がかかる構造。

- 出品者の入金スケジュールを**月次**にする（Stripe 側で設定可能）
- 「入金は毎月○日」と規約と出品者ダッシュボードに明記する

**出品者にとっても、少額が何度も振り込まれるより月1回まとまるほうが管理しやすい。**

## 3. レバー② 失敗・返金・チャージバックを減らす

### All-or-Nothing の締切時決済（最大の穴）

[06-stripe.md](06-stripe.md) のとおり、締切時の off_session 決済は**数%が必ず失敗する**。
これは手数料率の議論よりインパクトが大きい。**成功率を1%上げるほうが、料率を0.1%下げるより効く。**

| 対策 | 効果 |
|---|---|
| **カード自動更新（Card Account Updater 相当）を有効化** | 期限切れ・再発行カードの失敗を大幅に減らせる。**募集期間が長いほど効く** |
| 締切3日前に「まもなく決済されます」メール | 残高不足を事前に防げる |
| 3DS が必要な場合の再認証フローを用意 | `authentication_required` を救える |
| 失敗後3日おきに3回リトライ | 給料日を跨ぐと成功することがある |
| 締切直前の支援は決済成功率が高い | 期間を無駄に長くしない（30〜45日が目安） |

### 3D セキュアの使いどころ（トレードオフ）

| | 適用する | 適用しない |
|---|---|---|
| チャージバック | **責任がカード会社に移る（liability shift）** | 自社リスク |
| 決済成功率 | 下がる（認証離脱） | 高い |

**全件適用はしない。** 金額と Radar のリスクスコアで出し分ける。

```ts
payment_method_options: {
  card: {
    request_three_d_secure: amount >= 30_000 ? 'any' : 'automatic',
  },
}
```

高額ほどチャージバック損失が大きいので、**高額だけ守る**のが合理的。

### 返金の実損を減らす

返金しても決済手数料は戻ってこない。¥10,000 を全額返金すると約 ¥360 の実損。

- 運営都合の返金は**プラットフォームの負担**（規約で明記）
- 出品者都合の返金は**出品者への求償**を規約に定める
- 支援者都合のキャンセルは、**All-or-Nothing の募集期間中のみ**に限定する
  （まだ決済していないので実損ゼロ。これが AON の隠れた利点）

### チャージバックを減らす

[11-payment-hardening.md](11-payment-hardening.md) の予防策がそのままコスト削減になる。
**明細表記（statement descriptor）をサービス名にする**のが最も効く。「身に覚えのない請求」が最大の原因。

## 4. レバー③ 手数料の負担者を設計する ★効果が大きい

これは**技術ではなく設計判断**。海外のクラファンや寄付サイトで広く使われている。

### 案A: 支援者に決済手数料の任意負担を提案する

```
┌────────────────────────────────────┐
│ 支援金額            ¥10,000        │
│                                    │
│ ☑ 決済手数料 ¥360 を負担して、     │
│   全額をクリエイターに届ける       │
│                                    │
│ お支払い合計        ¥10,360        │
└────────────────────────────────────┘
```

- **デフォルトでチェックを入れておく**（ただしオプトアウトを明確に。ダークパターンにしない）
- 「あなたの支援が満額届きます」という体験は、支援者にとってもポジティブ
- 実際に多くの人が受け入れる

**効果:** 出品者への還元率を上げられる、またはプラットフォーム手数料を下げて見せられる。

⚠️ **法務注意:** 総額表示を必ず守る。最終的な支払額を明確に表示し、
チェックボックスを分かりにくくしない。**同意なく加算するのは絶対にダメ。**

### 案B: 料率の見せ方を分解する

```
✕  手数料 13.6%
○  手数料 13.6%（サービス利用料 10% + 決済手数料 3.6%）
```

同じ数字でも、**決済手数料が外部コストであることが伝わる**と納得されやすい。
「うちが 13.6% 取っている」ではなく「うちの取り分は 10%」という理解になる。

### 案C: 立ち上げ期の戦略的な低料率

初期は案件数がゼロなので、**手数料の安さが唯一の武器**になる。

```
🎉 リリース記念: 先着20プロジェクトはサービス利用料 0%
   （決済手数料 3.6% のみ）
```

- 原価（決済手数料）は必ず回収する。**赤字で決済を回してはいけない**
- 期限と件数を明示して、後で戻せるようにする
- [03-db-schema.md](03-db-schema.md) で `Project.platformFeeRate` をプロジェクト単位に持たせてあるので、
  **既存案件の条件を変えずに料率を変更できる。** この設計が効いてくる

### 案D: リターン価格の設計で単価を上げる

日本円の決済手数料は**定額部分がなく純粋な率**なので、支援単価を上げてもコスト率は変わらない。
ただし、**送金回数・メール送信数・サポート対応は件数に比例する**ので、
単価が高いほうが1円あたりの運用コストは下がる。

- リターンの価格帯を ¥3,000 / ¥10,000 / ¥30,000 のように広く取る
- 上乗せ支援（tip）を分かりやすい位置に置く

## 5. レバー④ 決済手段のミックス

カード以外の手段は、料率の構造が違うことがある。**特に高額支援で効く可能性がある。**

| 手段 | 特徴 | 検討 |
|---|---|---|
| カード | 標準。即時完了・UX が最良 | 主軸 |
| **銀行振込 / バーチャル口座** | 高額で有利になることがある。**要見積り** | 高額支援の受け皿として検討 |
| コンビニ決済 | 未成年・カード非保有層を取り込める | 到達率を上げる目的 |
| ウォレット系（PayPay 等） | 若年層に強い | 到達率を上げる目的 |
| Apple Pay / Google Pay | カード扱い。料率は同じ | **入れる。成功率が上がる** |

### 判断のしかた

```
高額支援（例: ¥50,000 以上）で銀行振込を提示する

  カード:     ¥50,000 × 3.6%  = ¥1,800
  銀行振込:   ¥50,000 × ??%   = ???     ← 要見積り

  差額が大きければ、高額支援だけ振込に誘導する価値がある
```

**ただし振込は「消込」の運用コストがかかる。** 入金確認・未入金の督促・期限管理が必要になり、
[01-requirements.md](01-requirements.md) でスコープ外にした理由がこれ。
**手数料差より運用コストのほうが大きくないか、必ず試算してから入れる。**

Apple Pay / Google Pay は料率が同じでも**決済完了率が上がる**（入力の手間がない）ので、
実質的な収益改善になる。Stripe Checkout なら設定だけで有効化できる。**これは早めに入れる。**

## 6. レバー⑤ 料率交渉

年間流通額が積み上がったら、PSP に個別料率を相談できるようになる。

**交渉に必要なもの:**

- [ ] 直近12ヶ月の流通額と件数
- [ ] チャージバック率（低いほど有利。**1%を超えると逆に不利**）
- [ ] 返金率
- [ ] 今後の成長見込み
- [ ] 他社の見積り（比較材料）

**チャージバック率を低く保つことが、将来の交渉力そのものになる。**
[11-payment-hardening.md](11-payment-hardening.md) の予防策は、目先の損失削減だけでなく、
ここに効いてくる。

## 7. レバー⑥ PSP の乗り換え（基本やらない）

候補としては、Stripe 以外にも国内 PSP が複数ある（PAY.JP、KOMOJU、GMO、SBペイメント、Square など）。
料率だけ見れば Stripe より安く見えるものもある。

### それでも Stripe から動かない理由

**マルチ出品者プラットフォームに必要な「本人確認込みの送金基盤（Connect 相当）」を
持っている PSP は限られる。**

料率が 0.6% 安くても、以下を自前で作ることになれば全く割に合わない:

- 出品者の本人確認（eKYC）
- 銀行口座の登録・検証
- 出品者ごとの残高管理
- 送金の実行と失敗ハンドリング
- 各種法定調書

**乗り換え判断の目安:** 年間流通額が1億円を超え、料率差が年間100万円以上になり、
かつ移行先が Connect 相当の機能を持っている場合に**初めて検討する**。

それまでは Stripe に固定し、**乗り換えではなく交渉で下げる。**

### ただし: 抽象化はしておく

将来の選択肢を残すため、決済処理を薄く抽象化しておく。作り込まなくていい。

```ts
// server/services/payment/provider.ts
export interface PaymentProvider {
  createCheckout(input: CheckoutInput): Promise<{ url: string; ref: string }>
  captureOffSession(input: CaptureInput): Promise<CaptureResult>
  refund(input: RefundInput): Promise<RefundResult>
  transferToCreator(input: TransferInput): Promise<TransferResult>
}
```

**Webhook の形式や Connect の概念まで抽象化しようとしない。** 漏れなく抽象化するのは不可能で、
やろうとすると複雑さだけが増える。**「差し替えるときに、どこを直せばいいかが分かる」程度で十分。**

## 8. 数値モデル

流通額（GMV）別に、ざっくりした収支感を掴む。**下の料率は例。実際の見積りで置き換えること。**

前提: サービス利用料 10%、決済手数料 3.6%、平均支援額 ¥8,000

| 年間 GMV | 支援件数 | 手数料収入(10%) | 決済原価(3.6%) | 粗利 | 備考 |
|---:|---:|---:|---:|---:|---|
| ¥1,000,000 | 125 | ¥100,000 | ¥36,000 | ¥64,000 | 趣味の範囲。**赤字にしないことが目標** |
| ¥10,000,000 | 1,250 | ¥1,000,000 | ¥360,000 | ¥640,000 | 副業として成立し始める |
| ¥50,000,000 | 6,250 | ¥5,000,000 | ¥1,800,000 | ¥3,200,000 | 料率交渉のテーブルにつける |
| ¥100,000,000 | 12,500 | ¥10,000,000 | ¥3,600,000 | ¥6,400,000 | 専業化を検討できる |

※ Connect の構造費用・返金・チャージバック・インフラ費は含まない。**実際の粗利はこれより下がる。**

### この表から読み取ること

**GMV ¥1,000万までは、料率を0.5%下げても年間5万円しか変わらない。**
その時間を「良いプロジェクトを1件増やす」ことに使ったほうが、GMV が何倍にもなる。

> **立ち上げ期のコスト最適化は、レバー①②③（送金まとめ・失敗削減・負担者設計）だけやって、
> あとは GMV を増やすことに集中する。** 料率交渉は後回しでいい。

## 9. インフラコストも見ておく

決済以外のランニングも、初期は無料枠でほぼゼロにできる。

| サービス | 無料枠 | 有料化の目安 |
|---|---|---|
| Vercel | Hobby は個人利用のみ。**商用は Pro が必要** | **最初から Pro が必要になる可能性が高い。要確認** |
| Neon (Postgres) | 無料枠あり | 数万レコードまでは無料枠で足りる |
| Cloudflare R2 | 無料枠あり・**egress 無料**が強い | 画像が増えても安い |
| Resend | 無料枠あり | 送信数が増えたら有料 |
| Sentry | 無料枠あり | そのまま |

**Vercel の Pro が必要かどうかは早めに確認する。** 商用利用の可否と、
[09-setup.md](09-setup.md) に書いた Cron の実行頻度制限の両方が絡む。
Cron が1日1回しか回せないと、締切処理と決済リトライの設計に影響する。

代替: Cron だけ GitHub Actions のスケジュール実行から HTTP を叩く形にすれば、
Vercel のプランに縛られずに毎時実行できる。**`CRON_SECRET` による保護は同じように必要。**
