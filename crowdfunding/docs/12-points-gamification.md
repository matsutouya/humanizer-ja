# 12. 応援ポイント / ゲーミフィケーション設計

「支援する側も楽しめる」ための仕組み。リポスト・引用でポイントが貯まる。

**ただし設計を間違えると、法務コストがサービス本体より重くなる。** 最初に境界線を引く。

---

## 0. 最重要の設計判断: ポイントは「換金も充当もできない」

### やっていい / ダメの線引き

| ポイントの使い道 | 可否 | 理由 |
|---|---|---|
| ランキング・順位の表示 | ✅ | 経済上の利益ではない。純粋な情報表示 |
| 称号・バッジ | ✅ | 同上 |
| プロフィールの装飾（フレーム・カラー） | ✅ | 同上。**自サイト内の表示だけで完結させる** |
| 限定コンテンツの閲覧権 | ⚠️ 当面やらない | 「経済上の利益」＝景品類に当たりうる。総付景品規制の対象 |
| 抽選応募（景品あり） | ⚠️ 当面やらない | 景品表示法の懸賞規制。設計が重くなる |
| **支援額への充当・値引き** | ❌ | 実質値引き＝景品類。総付景品規制（取引価額の20%）に乗る |
| **現金・ギフト券への交換** | ❌ | 資金決済法・景表法・税務が一気に絡む |
| **ユーザー間の譲渡・売買** | ❌ | 換金市場ができる。マネロンの温床 |
| 有償での購入 | ❌ | **前払式支払手段に該当。資金決済法の登録・供託義務** |

### 初期リリースの結論: **ポイントは「交換できない」**

ポイントで**何かと引き換えられる時点で「経済上の利益の提供」になり、景品表示法の景品規制が付いてくる。**
限定コンテンツですら、支援に付随して提供すれば景品類に当たりうる。

そこで初期は徹底的に安全側に倒す:

> **ポイントは、ランキング・称号・バッジの表示にのみ使う。何とも交換できない。**

これなら「経済上の利益の提供」が存在しないので、景品規制の議論に入る必要がそもそもなくなる。
交換所や抽選は、**弁護士の確認が取れてから**追加する（[08-roadmap.md](08-roadmap.md) の Phase 9 以降）。

限定コンテンツを配りたい場合は、**ポイント交換にせず「全支援者に提供する」形にする。**
それは景品ではなく「リターンの一部（取引そのものの内容）」なので、規制の枠組みが変わる。

### なぜ「支援に使える」にしないのか

一見ユーザーに喜ばれるが、こうなる:

1. ポイントが実質的な値引き = 景品表示法の「景品類」に該当しうる
2. 総付景品の上限は**取引価額の20%**。¥10,000 の支援なら ¥2,000 相当まで
3. 上限を計算・検証する仕組みが要る
4. さらに「ポイント分を誰が負担するか」問題が発生する。出品者の受取額を削るのか、プラットフォームが負担するのか
5. 会計上、未使用ポイントが**将来の値引き債務**になる

得られるものに対してコストが大きすぎる。**非換金・非充当に振り切る。**

> ⚠️ 無償で配布するポイント自体は、対価を得て発行するものではないため前払式支払手段には該当しないのが一般的な整理。ただし**有償ポイントを1円でも混ぜた瞬間に話が変わる**。「ポイント購入」機能は絶対に作らない。ここは [10-legal.md](10-legal.md) と合わせて弁護士に確認する項目。

### 抽選をやる場合の注意（重要な区別）

| 種類 | 参加条件 | 景品の上限 |
|---|---|---|
| **オープン懸賞** | 支援不要（リポートや登録だけで参加できる） | 金額上限の規制は撤廃済み |
| **一般懸賞（クローズド）** | 支援が参加条件になっている | 取引価額の20倍・最高10万円、総額は売上予定総額の2% |

つまり **「支援して得たポイント」で応募できる抽選は規制が厳しく、「リポストで得たポイント」だけの抽選は緩い。**

→ **設計に落とす:** ポイントに「取引に紐づくか」のフラグを持たせ、抽選の応募には**取引非連動ポイントしか使えない**ようにする。これで規制の重い側を回避できる。

```prisma
model PointTransaction {
  // ...
  /// true = 支援に紐づいて付与された（一般懸賞の規制対象）
  /// false = 支援と無関係に付与された（オープン懸賞として扱える）
  transactionLinked Boolean @default(false)
}
```

※ 実際の該当性判断は個別事情による。**抽選を実装する前に必ず専門家に確認する。** 初期は抽選を作らず、ランキング・称号だけで始めるのが安全。

## 0.5. 見落としやすい2つの規制 ★必読

「リポストでポイント」という仕組みには、景品規制とは別に**2つの規制が刺さる**。
どちらも知らずに作ると、サービス開始後に作り直しになる。

### (1) ステルスマーケティング規制

2023年10月から、景品表示法の指定告示として**ステマが不当表示に指定されている**。

問題になる構図はこれ:

```
事業者（＝うちのプラットフォーム）
      │ ポイントという「対価」を提供
      ▼
一般ユーザーが「このプロジェクトいいよ」と投稿
      ▼
第三者の自主的な感想に見えるが、実際は事業者が対価を出している
      ▼
★「事業者の表示」と判断されうる → 広告であることを明示しないと違反
```

**「ポイントをあげるから投稿して」は、対価の提供にあたる。** 金銭でなくても、経済的価値や便益があれば同じ扱いになりうる。ポイントに換金価値を持たせない設計にしていても、「ランキングが上がる」という便益がある以上、安全側で考えるべき。

しかも規制の名宛人は**投稿したユーザーではなく事業者**。つまり責任を負うのは投稿者ではなくこちら側。

#### 対策（必ず全部やる）

- [ ] **シェア用のテンプレート文に広告表示を最初から入れておく**

```ts
// シェア intent URL の生成
const text = [
  `${project.title} を応援しています！`,
  ``,
  `#PR #FUNDBEAT応援キャンペーン`,     // ★ 削除されにくいよう本文に含める
  shareUrl,
].join('\n')

const intent = `https://x.com/intent/post?text=${encodeURIComponent(text)}`
```

- [ ] シェアボタンの近くに明記する
  > このキャンペーンでは、シェアによってポイントが付与されます。
  > 投稿には必ず `#PR` を含めてください。
- [ ] キャンペーンページ・利用規約に、対価が発生することを明示する
- [ ] ユーザーがテンプレートを消して投稿した場合に備え、**規約で「広告表示のない投稿はポイント対象外」と定める**
- [ ] 出品者が支援者に拡散を依頼する機能を作る場合も、同じ表示ルールを適用する

**「#PR を消されたら検知できない」問題は残る。** だからこそ、シェア申告ポイントは少額に抑え、主軸を紹介リンク方式に置く（後述）。報酬が小さければ、規制上のリスクも実務上のインセンティブも小さくなる。

> ⚠️ ステマ規制の該当性は個別判断。**キャンペーンを始める前に必ず弁護士に確認する。**

### (2) 紹介報酬の多段階化は絶対にやらない

紹介報酬を**多段階**（自分が紹介した人がさらに紹介したら、自分にも入る）にすると、
特定商取引法の**連鎖販売取引（いわゆるマルチ商法）**に該当する可能性が出てくる。

該当すると、概要書面・契約書面の交付義務、クーリングオフ、広告規制など、
**個人で運営できる範囲を完全に超える義務**が発生する。

#### 守るルール

- [ ] **紹介報酬は1段階のみ。** 「紹介した人の紹介」には一切ポイントを出さない
- [ ] 紹介者に**金銭・換金可能なもの**を渡さない（ポイントを非換金にしている理由のひとつ）
- [ ] 「紹介すると稼げる」という訴求をしない。あくまで「応援の可視化」として設計する
- [ ] 紹介するために支援や登録料の支払いを条件にしない

```ts
// 実装上の防波堤: 紹介の連鎖を辿らない
// ReferralClick は referrerId を1つしか持たない。
// 「紹介者の紹介者」を辿るコードを絶対に書かない。
```

**この2つは、スキーマではなく「作らないこと」で守る。** 便利そうに見えても手を出さない。

## 1. 全体像

```
      ┌─────────────── 獲得 ───────────────┐
      │                                    │
  支援する            拡散する          参加する
  ・初回支援          ・紹介リンク経由    ・コメント
  ・支援するたび        の支援成立 ★核心  ・活動報告を読む
  ・成立に立ち会う    ・リポスト/引用      ・プロフィール完成
      │                                    │
      └──────────► ポイント台帳 ◄──────────┘
                        │
      ┌─────────────── 使う ───────────────┐
      │                │                   │
   サポーターランク   ランキング        限定コンテンツ
   （自動で上がる）   （全体/案件別）    （交換）
```

**「使う」より「貯まる／見える」を主軸にする。** 交換所を作り込むと運用コストが増える割に、ユーザーが一番嬉しいのは**自分の貢献が可視化されること**。ここに投資する。

## 2. 拡散の検証方法 — ここが設計の肝

「リポストしたらポイント」を素直に作ると、**検証できない or 検証コストが高すぎる**という壁に必ずぶつかる。

### 3つの選択肢

| 方式 | 検証精度 | コスト | 不正耐性 | 採用 |
|---|---|---|---|---|
| A. **紹介リンク経由の支援成立** | 高 | ゼロ | **非常に高い** | **◎ 主軸** |
| B. シェア申告 + スポットチェック | 低 | 低 | 中（少額なら許容） | ○ 補助 |
| C. X API で投稿を検証 | 高 | **高い** | 高 | ✕ 初期はやらない |

### なぜ C（X API）を採用しないか

- 投稿やリポストを読み取る API は有料プランが必要で、**月額コストが読めない**
- 利用規約と料金体系の変更が頻繁で、**サービスの中核機能を他社の都合に人質に取られる**
- スクレイピングでの代替は規約違反

**リポストを直接検証しようとするのをやめる。** 代わりに「拡散の**結果**」を計測する。

### A: 紹介リンク方式（主軸）

```
1. ユーザーが「シェアする」を押す
     → 紹介コード付き URL を生成
       https://fundbeat.jp/projects/my-song?ref=u_a1b2c3
     → X / LINE のシェア画面が開く（intent URL。API 不要）

2. 誰かがそのリンクを踏む
     → サーバーで ref を検証し、署名付き Cookie に保存（30日）
     → ProjectReferralClick を記録（1日1IPあたり上限つき）

3. その人が支援して CAPTURED になった
     → ★ ここで初めて紹介者にポイント付与
     → 「あなたのシェアから3人が支援しました」と可視化
```

**ポイントの発火点を「支援成立」に置くのが決定的に重要。**

- ボットにクリックさせても支援は発生しないので、**クリック水増しが無意味になる**
- 検証コストがゼロ（自分の DB で完結）
- X 以外（LINE・Instagram・ブログ・口コミ）も同じ仕組みで拾える
- 出品者にとっても「誰が広めてくれたか」が分かる

### B: シェア申告（補助・少額）

「シェアしました」ボタンで少額（+20pt 程度）を付与する。検証はしない。

- 1プロジェクトにつき1日1回まで
- 全体で1日100pt まで
- **少額に抑える。** これで稼げてしまうと制度が壊れる
- 投稿 URL の任意提出欄を設け、抽選でスポットチェック。虚偽が確認できたらポイント没収＋警告

「厳密に検証できないなら、そもそも報酬を小さくする」という割り切り。**検証コストと報酬額を釣り合わせる。**

### 拡散を「楽しく」する仕掛け（ポイントより効く）

ポイントより、**自分の影響が数字で返ってくること**のほうが継続する。

- 「あなたのシェアから **127人** が見て、**8人** が支援しました」
- 「あなたの紹介で集まった金額 **¥84,000**」
- プロジェクトごとの**応援ランキング**（支援額ではなく**拡散貢献**で並べる）
- 達成の瞬間に、貢献した人全員へ「一緒に達成しました」通知
- 「**23人目**の支援者です」という順番の表示（早期支援者の特別感）

**支援額ランキングだけにしない。** 金額で並べると、お金を出せない人が疎外される。拡散・コメント・継続を含む「貢献度」で並べると、誰でも上位を狙える。

## 3. ポイント台帳

**お金と同じ規律で扱う。** 残高を直接 UPDATE しない。取引を append-only で積み、残高はその集計（＋キャッシュ）。

```prisma
enum PointReason {
  SIGNUP                  // 会員登録
  PROFILE_COMPLETE        // プロフィール完成
  FIRST_PLEDGE            // 初回支援
  PLEDGE                  // 支援するたび
  PROJECT_SUCCEEDED       // 支援したプロジェクトが成立
  REFERRAL_PLEDGE         // ★ 紹介リンク経由で支援が成立
  REFERRAL_CLICK          // 紹介リンクの初回訪問（上限つき・少額）
  SHARE_DECLARED          // シェア申告
  COMMENT                 // コメント投稿
  CAMPAIGN                // 運営キャンペーン
  SPEND_EXCHANGE          // 交換で消費（マイナス）
  REVOKE_FRAUD            // 不正による没収（マイナス）
  REVOKE_REFUND           // 元の支援が返金された（マイナス）
  ADJUSTMENT              // 運営調整（要理由・要操作者）
  EXPIRE                  // 有効期限切れ（マイナス）
}

model PointAccount {
  userId         String   @id
  user           User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  balance        Int      @default(0)   // キャッシュ。台帳から再計算可能
  lifetimeEarned Int      @default(0)   // ランク判定に使う（消費しても減らない）
  updatedAt      DateTime @updatedAt

  @@index([balance])
  @@index([lifetimeEarned])
}

model PointTransaction {
  id     String      @id @default(cuid())
  userId String
  user   User        @relation(fields: [userId], references: [id])

  amount Int                    // 符号付き。付与+ / 消費・没収−
  reason PointReason

  /// 冪等キー。"REFERRAL_PLEDGE:<pledgeId>" のように一意に決まる文字列。
  /// unique 制約により、同じ事象で二重付与されない。
  externalRef String @unique

  refType String?   // "Pledge" | "Project" | "Comment" ...
  refId   String?

  /// 景品規制の区分。支援に紐づいて付与されたポイントは true。
  transactionLinked Boolean @default(false)

  expiresAt DateTime?          // 有効期限（付与から2年など）
  memo      String?  @db.Text
  operatorId String?           // ADJUSTMENT / REVOKE_FRAUD では必須

  createdAt DateTime @default(now())

  @@index([userId, createdAt])
  @@index([reason, createdAt])
  @@index([expiresAt])
}

/// 紹介リンクのクリック記録。不正検知と可視化の両方に使う。
model ReferralClick {
  id         String  @id @default(cuid())
  referrerId String                       // 紹介した人
  projectId  String
  visitorId  String?                      // ログイン済みなら userId
  ipHash     String                       // 生 IP は保存しない（ハッシュ + ソルト）
  uaHash     String
  converted  Boolean @default(false)      // 支援に至ったか
  pledgeId   String?

  createdAt DateTime @default(now())

  @@index([referrerId, createdAt])
  @@index([projectId, createdAt])
  @@index([ipHash, createdAt])
}
```

### 付与ヘルパー

```ts
export async function grantPoints(
  tx: Prisma.TransactionClient,
  input: {
    userId: string; amount: number; reason: PointReason
    externalRef: string; transactionLinked?: boolean
    refType?: string; refId?: string; memo?: string; operatorId?: string
  }
): Promise<boolean> {
  if (input.amount === 0) return false
  if (['ADJUSTMENT', 'REVOKE_FRAUD'].includes(input.reason) && !input.operatorId) {
    throw new Error('operatorId required')
  }

  try {
    await tx.pointTransaction.create({
      data: { ...input, expiresAt: addYears(new Date(), 2) },
    })
  } catch (e) {
    if (isUniqueViolation(e, 'externalRef')) return false   // 付与済み。冪等
    throw e
  }

  await tx.pointAccount.upsert({
    where:  { userId: input.userId },
    create: { userId: input.userId, balance: input.amount,
              lifetimeEarned: Math.max(0, input.amount) },
    update: {
      balance:        { increment: input.amount },
      // 消費・没収では lifetimeEarned を減らさない
      lifetimeEarned: { increment: Math.max(0, input.amount) },
    },
  })
  return true
}
```

**`externalRef` の設計がすべて。** `REFERRAL_PLEDGE:<pledgeId>` のように**事象から一意に決まる文字列**にする。`Date.now()` や乱数を混ぜたら冪等性が消える。

### 整合性チェック（[11-payment-hardening.md](11-payment-hardening.md) の照合バッチに追加）

```sql
-- 残高キャッシュが台帳と一致しているか
SELECT a."userId", a.balance, COALESCE(SUM(t.amount), 0) AS actual
FROM "PointAccount" a
LEFT JOIN "PointTransaction" t ON t."userId" = a."userId"
GROUP BY a."userId", a.balance
HAVING a.balance <> COALESCE(SUM(t.amount), 0);

-- 残高がマイナスになっていないか
SELECT "userId" FROM "PointAccount" WHERE balance < 0;
```

## 4. 獲得ルール表

| 行動 | pt | 上限 | 取引連動 | 検証 |
|---|---:|---|---|---|
| 会員登録 | 50 | 1回のみ | false | 自動 |
| プロフィール完成（アイコン+自己紹介） | 30 | 1回のみ | false | 自動 |
| 初回支援 | 200 | 1回のみ | **true** | 自動 |
| 支援するたび | 支援額の1%相当 | 1回あたり 1,000pt | **true** | 自動 |
| 支援したプロジェクトが成立 | 100 | プロジェクトごと | **true** | 自動 |
| **紹介リンク経由で支援が成立** | **300** | 1日 3,000pt | false | 自動 ★核心 |
| 紹介リンクの初回訪問 | 1 | 1日 50pt | false | 自動（IP 単位で重複排除） |
| シェア申告 | 20 | 1プロジェクト1日1回 / 1日 100pt | false | なし（スポットチェック） |
| コメント投稿 | 5 | 1日 3回 | false | 自動 |
| 活動報告への反応 | 2 | 1日 10pt | false | 自動 |

**1ユーザーの1日獲得上限を 5,000pt にする。** 上限がないと、抜け道が見つかったときに被害が青天井になる。

### 支援額連動ポイントの注意

「支援額の1%」は**取引連動（`transactionLinked: true`）**として記録する。抽選に使えるのは非連動ポイントのみなので、UI でも分けて表示する。

```
保有ポイント  1,250 pt
  ├ 抽選に使えるポイント   450 pt
  └ ランク判定のみ        800 pt
```

## 5. サポーターランク

消費とは別に、`lifetimeEarned` で自動的に上がる。**何もしなくても上がっていくのが気持ちいい。**

| ランク | 累計 | 特典 |
|---|---:|---|
| 🌱 ルーキー | 0 | — |
| 🎵 サポーター | 500 | プロフィールにバッジ |
| 🔥 コアサポーター | 3,000 | バッジ + プロフィール装飾 |
| 💎 アンバサダー | 10,000 | 上記 + 応援ランキング常設掲載 |
| 👑 レジェンド | 50,000 | 上記 + 専用バッジデザイン |

**特典は「サイト内の表示」だけに限る。** 金銭的価値のあるもの、モノ、外部で使えるものは一切入れない。

⚠️ **「新着プロジェクトの先行通知」「限定コンテンツ」をランク特典にしない。**
一見無害だが、支援を通じて得たランクに紐づく便益は「取引に付随する経済上の利益」として
景品類に当たりうる。判断が必要になる時点で設計として重い。**表示だけに留めれば議論が発生しない。**

### ランクは降格させない

「使わないと下がる」は不安を煽るだけで、離脱を招く。**上がる一方**にする。
代わりに、ランキングは**シーズン制**（3ヶ月ごとにリセット）にして、新規ユーザーにも上位のチャンスを作る。

## 6. 不正対策

ポイントに価値が生まれた瞬間、必ず抜け道を探す人が現れる。

### 自己紹介の遮断（最優先）

```ts
async function isSelfReferral(referrerId: string, pledge: Pledge): Promise<boolean> {
  if (referrerId === pledge.backerId) return true                       // 同一アカウント

  const clicks = await prisma.referralClick.findMany({
    where: { referrerId, pledgeId: pledge.id },
  })
  const referrer = await getRecentSignals(referrerId)

  return (
    clicks.some(c => c.ipHash === referrer.lastIpHash) ||               // 同一 IP
    (await sameCardFingerprint(referrerId, pledge)) ||                  // 同一カード
    (await sameShippingAddress(referrerId, pledge))                     // 同一配送先
  )
}
```

**カードのフィンガープリント一致が一番効く。** Stripe が `payment_method.card.fingerprint` を返すので、同一カードでの自己紹介・多重アカウントを高精度で検出できる。

### 付与を保留する

紹介ポイントは**即時付与しない**。

```
支援 CAPTURED
   ↓ 保留（PENDING）
   ↓ 7日経過 かつ 返金・チャージバックなし
   ↓
 確定して付与
```

返金が確定してからポイントを配ると、「支援→ポイント獲得→キャンセル」の抜け道が塞がる。
返金が発生したら `REVOKE_REFUND` でマイナス記帳する（残高がマイナスになることは許容し、次回獲得分で相殺する）。

### その他

| 攻撃 | 対策 |
|---|---|
| 多重アカウント作成 | メール確認必須。登録から7日間は紹介ポイント対象外 |
| ボットによるクリック水増し | クリック単体では 1pt しか出ない。IP 単位で重複排除 + 1日上限 |
| コメント連投 | 1日3回まで。最低文字数（20文字） |
| シェア申告の虚偽 | 少額に抑える。抽選でスポットチェック。悪質なら没収＋アカウント停止 |
| ポイントの譲渡・売買 | **譲渡機能を作らない。** 規約で禁止し、検知したら没収 |

### 規約に必ず書くこと

- ポイントに換金価値はなく、譲渡・売買できない
- 不正が確認された場合、運営はポイントを取り消せる
- ポイント制度は運営の裁量で変更・終了できる（**終了時の扱いを明記**）
- 有効期限（最終獲得から2年など）
- 退会時にポイントは消滅する

## 7. ポイント以外の「楽しさ」

ポイントは仕組みの一部でしかない。**支援した瞬間の体験**のほうが記憶に残る。

### 支援直後

- 達成率が動くアニメーション（自分が押し上げた実感）
- 「あなたは **23人目** の支援者です」
- 「目標まであと **¥42,000**」（自分の支援で残りが減った実感）
- シェアカードの自動生成（「このプロジェクトを応援しました」画像を X に投稿できる）

### 募集期間中

- 目標達成の瞬間、支援者全員に「達成しました！」通知
- 残り24時間で「ラストスパート」通知（支援者に拡散を依頼する）
- 出品者からの活動報告（支援者限定）
- プロジェクトページに支援者のアイコンが並ぶ（匿名は除く）

### 成立後

- 「達成に立ち会った人」バッジ
- 完成した曲を支援者に先行公開
- 支援者名のクレジット掲載（リターンとして）

**音楽プロジェクトなら「完成した曲が支援者に先に届く」が最強の体験。** ポイント制度より、ここを作り込む価値のほうが高い。

## 8. 実装フェーズ

ポイントは**サービスの本体ではない**。決済が固まるまで手を出さない。

| Phase | 内容 | 前提 |
|---|---|---|
| **9-a** | 紹介リンク（`?ref=`）+ クリック計測 + 可視化（**ポイントなし**） | Phase 5 完了後 |
| **9-b** | `PointAccount` / `PointTransaction` + 基本の獲得ルール | 9-a + **規約整備** |
| **9-c** | サポーターランク + バッジ表示 | 9-b |
| **9-d** | ランキング（全体・案件別・シーズン制） | 9-c |
| **9-e** | シェア申告 + `#PR` テンプレート + スポットチェック運用 | 9-d + **ステマ規制の確認** |
| （保留） | 限定コンテンツ交換 | **弁護士確認が完了してから** |
| （保留） | 抽選機能 | **弁護士確認が完了してから** |

**9-a には法務論点がほぼない。** ポイントという対価を出さないので、ステマ規制も景品規制も問題にならない。
それでいて「自分のシェアから何人が支援したか」が見えるだけで、拡散のモチベーションはかなり上がる。

**まず 9-a だけ作って様子を見るのを強く推奨する。** 効果が確認できてから 9-b 以降に進めば、
法務コストをかける判断が数字に基づいてできる。

## 9. 実装チェックリスト

### 法務まわり（最優先）

- [ ] ポイントは換金・支援充当・譲渡ができない
- [ ] **ポイントは何とも交換できない**（表示・称号・ランキングのみ）
- [ ] 有償ポイントの購入機能を作っていない
- [ ] **紹介報酬が1段階のみ**（紹介者の紹介者に報酬が出ない）
- [ ] 「紹介で稼げる」という訴求をしていない
- [ ] **シェアテンプレートに `#PR` が最初から入っている**
- [ ] シェアボタン付近に「ポイントが付与されること」を明記している
- [ ] 規約に「広告表示のない投稿はポイント対象外」と書いてある
- [ ] ランク特典に金銭的価値・モノ・外部で使えるものが含まれていない
- [ ] `transactionLinked` で取引連動/非連動を区別している
- [ ] 抽選・限定コンテンツ交換は弁護士確認が済むまで実装しない
- [ ] **キャンペーン開始前に弁護士のレビューを受けた**

### 実装まわり
- [ ] `PointTransaction` が append-only で `externalRef` に unique 制約がある
- [ ] `grantPoints` を経由しないポイント操作がない
- [ ] 残高キャッシュの整合性チェックが毎日走る
- [ ] 紹介ポイントの発火点が「支援成立」になっている
- [ ] 自己紹介判定（同一アカウント / IP / カード / 配送先）が入っている
- [ ] 紹介ポイントを7日間保留してから確定している
- [ ] 返金時にポイントを回収している
- [ ] 1日あたりの獲得上限がある
- [ ] IP を生のまま保存していない（ハッシュ + ソルト）
- [ ] X API に依存していない
- [ ] 規約にポイントの性質・変更/終了・失効・不正時の取消を明記した
