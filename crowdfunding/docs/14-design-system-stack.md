# 14. デザインシステムの技術選定

「どのデザインシステムを使うか」の結論と、その根拠。
[07-design.md](07-design.md) が**見た目の仕様**なら、これは**それを何の上に載せるか**の判断。

調査日: 2026年8月

---

## 0. 結論

**既製のデザインシステムを丸ごと採用しない。3層に分けて、層ごとに最適なものを選ぶ。**

```
┌─────────────────────────────────────────────────┐
│ 第3層  配布       shadcn/ui CLI                  │  コピーして取り込む
│                  （依存にしない）                  │
├─────────────────────────────────────────────────┤
│ 第2層  振る舞い    Base UI                        │  ← Radix ではなく
│        a11y      （キーボード操作・ARIA・フォーカス）│
├─────────────────────────────────────────────────┤
│ 第1層  トークン    自前                            │  07-design.md
│        見た目     CSS Custom Properties           │  Tailwind v4 @theme
└─────────────────────────────────────────────────┘

参照するが依存しない:
  デジタル庁デザインシステム（DADS） … 日本語フォーム・アクセシビリティの規範
  SmartHR Design System            … 日本語 UX ライティングの規範
```

**要点を3行で。**

1. **見た目（第1層）は自前**。既製システムを採用すると「そのシステムに見える」ので、ブランドが立たない
2. **振る舞い（第2層）は絶対に自前で書かない**。フォーカストラップ・キーボード操作・ARIA を自作すると必ず壊れる
3. **第2層は Radix ではなく Base UI**。2026年時点でこれが逆転している（§2）

---

## 1. なぜ既製のデザインシステムを「丸ごと」採用しないのか

まず検討した候補と、却下理由。

| 候補 | 性格 | 却下理由 |
|---|---|---|
| Material Design 3 | Google の総合システム | **Google に見える。** 日本の消費者向けサービスで Material をそのまま使うと「Android アプリ感」が出る。装飾が強く、白基調のマーケットプレイスと合わない |
| Ant Design | 業務システム向け | 情報密度が高く**管理画面の見た目**。消費者向けの温度感がない |
| Chakra / Mantine | オールインワン | 見た目と振る舞いが密結合。デザインを寄せていくと結局全部上書きすることになり、ライブラリの利点が消える |
| Shopify Polaris | EC 管理画面 | 管理画面専用。公開ページ側の語彙がない |
| GitHub Primer / Atlassian | 自社製品専用 | 外部利用を想定していない |
| **デジタル庁 DADS** | 行政サービス向け | **後述。参照はする（§4）が、丸ごとは使わない** |

### 却下の共通理由

**クラウドファンディングは「信用」と「熱量」を同時に伝える必要がある。**
行政システムの規範（信用・中立・無機質）でも、業務システムの規範（密度・効率）でもない。
既製システムはどれかに最適化されているので、そのまま使うと**プロダクトの性格とズレる**。

一方で、**振る舞いとアクセシビリティは車輪の再発明をしてはいけない**。
モーダルのフォーカストラップ、コンボボックスのキーボード操作、`aria-*` の正しい付与は、
自作すると必ずどこかが壊れる。ここは実績あるライブラリに任せる。

だから**分離する**。これが結論。

## 2. 第2層: Base UI を選ぶ（Radix ではなく）

### 2.1 これは2026年に逆転した判断

数年前なら Radix UI 一択だった。いまは違う。候補は実質4つある。

| | **Base UI** ★採用 | Radix UI | React Aria | Ark UI |
|---|---|---|---|---|
| 開発元 | MUI ＋ Radix / Floating UI の元コントリビュータ | Modulz → **WorkOS が買収** | **Adobe** | Chakra チーム |
| 安定版 | **v1.0 到達済み** | v1 到達済み | 長期に安定 | v安定 |
| 保守状況 | **専任チームが長期保守を明言** | 主要メンテナが離脱し更新が鈍化。買収元が再投資中 | Adobe が製品基盤として維持。**最も安泰** | 活発 |
| 規模 | 35コンポーネント | 30+ | **40+ パターン**（hooks ＋ components） | 多数・複数フレームワーク対応 |
| Combobox | **あり** | なし | あり | あり |
| i18n | 標準的 | 標準的 | **30言語超・13暦法・数値/日付ローカライズ・RTL** | 標準的 |
| API | `render` prop | `asChild` | hooks ＋ RAC。State 層（React Stately）が別 | ステートマシン（Zag.js） |
| shadcn/ui | **既定** | サポート継続 | 非既定 | 非既定 |
| 学習コスト | 低 | 低 | **高**（概念が多い） | 中 |

### 2.2 なぜ React Aria ではないのか（ここが一番迷った）

**アクセシビリティの深さだけを見れば React Aria が最強。** WAI-ARIA APG に忠実で、
キーボード操作・スクリーンリーダー・フォーカス管理・タッチが production で鍛えられている。
Adobe が自社製品の基盤として維持しているので、**保守の継続性も4つの中で最も確か**。

それでも採用しない理由は3つ。

1. **i18n の深さが、このプロダクトでは使われない。**
   React Aria の強みは30言語超・13暦法・ロケール別の数値/日付書式。
   だがこのサービスは **`ja-JP` 単一・円のみ・西暦のみ**（[01-requirements.md](01-requirements.md) でスコープ外に明記）。
   最大の差別化要因が、まるごと死に荷になる。

2. **概念が多く、実装者1人には重い。** Aria（振る舞い）／Stately（状態）／Internationalized（i18n）が
   層に分かれている。設計としては正しいが、**Phase 5 まで最短で到達する**という
   このプロジェクトの最優先事項と噛み合わない。

3. **shadcn/ui の既定ではない。** 第3層（§3）と噛み合わず、コンポーネントを自前で書く量が増える。

> **React Aria に切り替えるべき条件。** 次のどれかが起きたら再検討する。
> - 多言語対応を始める（英語版を出す等）
> - JIS X 8341-3 の適合表明が必要になる（自治体案件・公的資金が絡む等）
> - 日付ピッカーなど、暦とロケールに強く依存する UI が中心になる
>
> いずれも現時点では該当しない。**該当した時点で第2層だけ差し替える**（§2.3）。

### 2.3 Base UI を選ぶ理由

1. **保守の継続性がリスクの中心。** Radix は買収後に主要メンテナが離脱し、
   issue と PR が滞留した経緯がある。決済を扱うプロダクトの土台を、
   保守が不透明なライブラリに置きたくない。Base UI は専任チームによる長期保守を明言している。
   （**この一点で Radix は落ちる**。機能面では依然として優秀）

2. **Combobox がある。** カテゴリ選択・都道府県選択・出品者検索で必ず必要になる。
   Radix にはなく、別ライブラリを足すことになる。依存が増えるほど壊れやすくなる。

3. **shadcn/ui の既定が Base UI に移った。** 第3層（§3）と素直に噛み合う。

4. **`render` prop のほうが明示的。** `asChild` は「子要素に props がマージされる」という
   暗黙の挙動で、ネストすると追いにくい。決済フローのように壊してはいけない画面では、
   明示的なほうがよい。

5. **必要十分。** 使うのは Dialog / Popover / Select / Combobox / Tabs / Tooltip /
   Checkbox / Radio / Switch / Toast 程度。**React Aria の深さを必要とする画面がない。**

### 2.4 リスクと備え

| リスク | 備え |
|---|---|
| Base UI が新しく、事例が Radix より少ない | 使うのは Dialog / Popover / Select / Combobox / Tabs / Tooltip / Checkbox / Radio / Switch / Toast 程度。枯れた領域しか使わない |
| 日本語 IME での挙動（Combobox の変換確定でイベントが暴発しないか） | **Phase 2 の試作で必ず実機確認する。** どのライブラリも公式には明言していない領域で、実測するしかない |
| API が変わる可能性 | shadcn 方式で**コードを自リポジトリに取り込む**（§3）。バージョン追従を強制されない |
| 万一 Base UI が停滞したら | 第1層（トークン）と第3層（コピー済みコード）は無傷。第2層だけ差し替えればよい。**そのための3層分離** |

**採用を確定する前に、Phase 2 の頭で Dialog と Combobox を1つずつ試作する。**
ドキュメントの読みやすさと、日本語入力の実挙動を実機で確かめてから本採用にする。
ここで問題が出たら、React Aria に切り替える（§2.2 の切替条件）。

## 3. 第3層: shadcn/ui の「配布方式」だけ借りる

shadcn/ui は**ライブラリではなくコードの配布方式**。CLI でコンポーネントのソースを
自分のリポジトリにコピーしてくる。npm 依存にならない。

```bash
npx shadcn@latest add dialog select combobox toast
# → components/ui/ に .tsx が置かれる。以後は自分のコード
```

### なぜこれが正解か

| | メリット |
|---|---|
| **デザインを自由に改変できる** | [07-design.md](07-design.md) のトークンに合わせて中身を書き換える。ライブラリの上書き合戦にならない |
| **バージョン地獄がない** | 依存ではないので、破壊的変更に振り回されない |
| **必要な分だけ** | 使わないコンポーネントがバンドルに入らない |
| **中身が読める** | 決済フローで挙動が怪しいとき、`node_modules` を追わずに済む |

### 運用ルール

1. **取り込んだ直後に、必ずトークンに合わせて書き換える。** デフォルトの見た目のまま使わない
2. **取り込んだコードは自分のコードとして扱う。** レビューもテストも自分の責任
3. **全部入れない。** 実際に使う画面ができてから、その都度足す

## 4. 参照するが依存しない2つ

### 4.1 デジタル庁デザインシステム（DADS）

日本語の公共サービス向けデザインシステム。**Figma・HTML・React のスニペットと、
デザイントークンのパッケージ（CSS Custom Properties / JS 変数）を提供**している。
ライセンスは**政府標準利用規約 2.0（CC BY 4.0 互換）**で、**民間企業でも利用・改変できる。**

#### 丸ごと使わない理由

行政サービス向けに最適化されていて、**中立・無機質**な方向。
クラウドファンディングに必要な「応援したくなる温度」がない。トップページに使うと役所のサイトになる。

#### それでも参照する価値が大きい理由

**日本語 UI のアクセシビリティで、これ以上に信頼できる規範が国内にない。**
特に以下は、自前で考えるより DADS の解を踏襲したほうが確実に良い。

| 参照する領域 | 具体的に |
|---|---|
| **フォーム** | 氏名・住所・電話番号・郵便番号の入力パターン。エラーの示し方、必須の示し方 |
| **アクセシビリティ** | JIS X 8341-3 / WCAG 2.2 AA を前提にした実装指針 |
| **日本語のコントラスト基準** | 和文は欧文よりウェイトが細く見えるため、同じ比率でも読みにくい。その扱い |
| **フォーカス表示** | 日本語 IME 環境での挙動 |
| **エラーメッセージの構造** | 何が・どこが・どう直すか |

**支援フローの住所入力**（[05-screens.md](05-screens.md)）は、DADS のパターンをほぼそのまま踏襲する。
ここで独自性を出す意味はゼロで、間違えると支援が完了しない。

> ライセンス表記の要否（CC BY 4.0 の帰属表示）は、**実際にコードやトークンを流用する場合に確認する**。
> パターンを参考にするだけなら不要だが、スニペットを取り込むなら [10-legal.md](10-legal.md) の確認事項に加える。

### 4.2 SmartHR Design System

日本語の **UX ライティング**で最も参考になる国内事例。
運営チームに UX ライターが在籍していて、日本語の言い回しの指針が具体的。

[07-design.md](07-design.md) §9（ライティング）は、この考え方を下敷きにしている。
**「エラーが発生しました」で終わらせない**、**ボタンは何が起きるかを書く**、といった原則。

## 5. 第1層: トークンの管理方法

### 5.1 3層のトークン（これは業界標準の型）

```
プリミティブ   accent/600 = #dc3520
      ↓        「色そのもの」。ここだけが hex を持つ
セマンティック  --accent-solid = var(--accent-600)
      ↓        「役割」。実装が参照するのはここだけ
コンポーネント  --button-primary-bg = var(--accent-solid)
               「用途」。必要になったときだけ作る
```

**コンポーネント層は最初から作らない。** 2層で足りる。
同じセマンティックトークンを別の値にしたいコンポーネントが出てきたときに初めて足す。

### 5.2 いまの実装方法: CSS Custom Properties を手書き

Tailwind v4 は JS 設定ファイルを廃止し、**CSS がそのまま設定になった**。
つまり CSS Custom Properties がネイティブのトークンシステムになっている。

```css
/* app/globals.css — これが唯一の真実 */
:root {
  --accent-solid: #dc3520;
  /* … 07-design.md §1.2 のとおり */
}

@theme inline {
  --color-accent-solid: var(--accent-solid);
  /* → bg-accent-solid / text-accent-solid が使えるようになる */
}
```

**いまはこれで十分。** ビルドステップを足さない。

### 5.3 将来: DTCG + Style Dictionary（まだやらない）

2026年の標準的なパイプラインはこう。

```
Figma Variables
     ↓  DTCG 形式（W3C Design Tokens。2025年10月に初の安定版）
tokens.json
     ↓  Style Dictionary（ビルド）
CSS変数 / Tailwind theme / JS定数 / iOS / Android
```

**導入する条件は「Figma がループに入ったとき」。**

いまは Figma を使っておらず、実装者も1人。この状態でビルドステップを足すと、
**トークンを1つ変えるたびにビルドを回す手間だけが増えて、得るものがない。**

導入すべきタイミング:

- デザイナーが Figma で作業を始め、Figma と実装の値がズレ始めたとき
- ネイティブアプリなど、CSS 以外の出力先が増えたとき

**逆に言えば、それまでは入れない。** ツールを増やすことは、それ自体がコストになる。

> 移行しやすくするための備え: [07-design.md](07-design.md) §1.2 のトークン名は、
> DTCG 形式にそのまま写せる粒度と命名にしてある。移行時に名前を変えずに済む。

## 6. その他の選定

| 領域 | 採用 | 理由 |
|---|---|---|
| アイコン | **Lucide** | MIT。線幅が均一で、日本語の細いフォントと相性がよい。tree-shakable。Material Icons は Google 色が出る |
| フォント | **OS フォント**（Web フォントなし） | 日本語 Web フォントは数百KB〜数MB。LCP が支援率に直結する（[07-design.md](07-design.md) §2.1） |
| チャート | 当面なし | 出品者ダッシュボードで必要になったら Recharts か軽量な自作 SVG。**進捗バーはチャートではない** |
| アニメーション | CSS のみ | Framer Motion 等は入れない。必要なのは `transition` と `@keyframes` 程度 |
| Figma | 当面なし | 実装者1人。実装が仕様になっている状態のほうが速い |

## 7. 導入の順番

```
Phase 0（済）
  第1層のトークンを globals.css に定義
  基本コンポーネント（Button / Card / Badge / ProgressBar）を手書き
  ↓
Phase 2（フォームが増えるとき）★ここが判断ポイント
  1. Base UI で Dialog を1つだけ試作
     - ドキュメントの読みやすさ
     - 日本語 IME での挙動（特に Combobox）
  2. 問題なければ shadcn CLI で必要分を取り込む
  3. 取り込んだ直後にトークンへ寄せる
  ↓
Phase 3（公開ページ）
  DADS を参照してフォームのアクセシビリティを詰める
  ↓
将来（Figma が入ったら）
  DTCG + Style Dictionary を導入
```

**Phase 2 まで、この判断を実行に移す必要はない。**
いま決めておく意味は、「Phase 2 で迷わないため」と「Phase 0 の作り方を間違えないため」。

Phase 0 で守るべきことは1つだけ:

> **コンポーネントの CSS に生の hex を書かない。必ずセマンティックトークン経由で書く。**

これさえ守れば、第2層・第3層はいつでも差し替えられる。破ると全部やり直しになる。

## 8. まとめ: なぜこの構成が「プロ仕様」なのか

| よくある失敗 | この構成での回避 |
|---|---|
| 既製システムをそのまま使い、どこかで見た見た目になる | 見た目（第1層）は自前 |
| ゼロから全部作り、モーダルのキーボード操作が壊れる | 振る舞い（第2層）は実績あるライブラリ |
| ライブラリのスタイルと戦い続ける | 配布方式（第3層）でコードを自分のものにする |
| ライブラリの保守が止まって詰む | 3層に分離してあるので、止まった層だけ差し替え |
| トークンを整備せず、色を変えられなくなる | セマンティックトークンを最初から強制 |
| 日本語のアクセシビリティを我流で解決する | DADS を規範として参照 |
| ツールを増やしすぎて運用が回らない | Style Dictionary は条件を満たすまで入れない |
