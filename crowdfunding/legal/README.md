## 使い方

### 1. `【要記入：X-N】` を埋める

すべてのプレースホルダは [../decisions.md](../decisions.md) の項目番号に対応しています。
決定事項シートを埋めてから、一括置換してください。

```bash
# 例
grep -rn '【要記入' legal/          # 残っている箇所を確認
```

**`【要記入】` が1つでも残っている状態で公開しないこと。**

### 2. `▶ 起草メモ` を削除する

`> ▶ 起草メモ` で始まる引用ブロックは、判断が必要な箇所や意図を説明した**内部向けメモ**です。
弁護士に渡すときは残したまま（論点が伝わるので有用）、**公開時には削除してください。**

```bash
# 公開前に検出
grep -rn '▶ 起草メモ' legal/
```

### 3. 弁護士に渡す

[../decisions.md](../decisions.md) の「G. 弁護士に確認する論点」と、この `legal/` 一式をまとめて渡します。
論点リストがあると、レビューの精度と速度が上がります。

### 4. 施行日を入れる

各文書の冒頭に制定日・施行日を記載します。**変更履歴も残してください**（規約変更の手続きで必要になります）。

## 公開前チェックリスト

- [ ] `【要記入】` が残っていない
- [ ] `▶ 起草メモ` を削除した
- [ ] 制定日・施行日を記載した
- [ ] 4文書の内容に矛盾がない（手数料率・返金条件・送金時期）
- [ ] [../decisions.md](../decisions.md) の値と一致している
- [ ] 実装の挙動と一致している（**規約に書いたことが実装されているか**）
- [ ] 弁護士のレビューを受けた
- [ ] 会員登録画面で規約への同意を取得している
- [ ] 支援画面で規約・キャンセル条件を再掲している

> **最後の3つが特に重要。** 規約に書いてあっても、実装が違えば意味がありません。
> 逆に、実装した機能が規約に書かれていないのも同じくらい危険です。
