# FUNDBEAT（仮）— 購入型クラウドファンディング・プラットフォーム

自分たちの曲を作る資金を集めるために始める、**誰でも出品できる**購入型クラウドファンディングサイト。
CAMPFIRE のようなマルチ出品者型プラットフォームを、まず自分たちのプロジェクトを第1号案件として立ち上げる。

> ✅ **Phase 0（環境構築）まで完了。動く Next.js プロジェクトになっている。**
> DB を用意しなくても、トップページと `/styleguide` は表示できる。

```bash
cd crowdfunding
npm install
npm run dev      # → http://localhost:3000
```

| コマンド | 内容 |
|---|---|
| `npm run dev` | 開発サーバー |
| `npm run build` | 本番ビルド |
| `npm test` | ユニットテスト（25件） |
| `npm run typecheck` | 型チェック |
| `npm run lint` | ESLint |
| `npm run db:migrate` | マイグレーション（**DB が必要**） |

| `npm run db:studio` | DB の中身をブラウザで確認（**DB が必要**） |

（[docs/09-setup.md](docs/09-setup.md)）。

## このプロジェクトの位置づけ

| | 内容 |
|---|---|
| 種類 | 購入型クラウドファンディング（リターン＝モノ・体験・デジタル音源など） |
| 出品者 | 自分たち＋一般ユーザー（誰でも申請して出品できる） |
| 支援者 | 一般ユーザー（会員登録あり） |
| 決済 | Stripe Connect（テストモードから開始） |
| 収益 | プラットフォーム手数料（支援額の一定％）＋ Stripe 決済手数料の転嫁 |
| 通貨 | 日本円のみ（JPY・整数管理） |

**寄付型・投資型ではなく購入型**に限定するのが重要。投資型（株式・ファンド）は金融商品取引法の登録が必要で、個人では現実的に不可能。寄付型も税務・法務が複雑になる。購入型なら「通信販売」の枠組みで整理できる。

```
Phase 7  活動報告・コメント・通知メール                           2〜3日
Phase 8  運営管理画面（審査・強制停止・返金）                     2〜3日

まず動かして人に見せられるのは Phase 5 まで（約2週間相当）
```

Phase 5 には**決済の堅牢化（台帳・状態機械・Outbox）が含まれる**。
これらは後付けが非常に高くつくので、最初の支援フローと同時に入れる。[11-payment-hardening.md](docs/11-payment-hardening.md)。

**Phase 5 が最初のマイルストーン。** ここまで来れば「自分たちの曲プロジェクトを出して、友達がカードで支援できる」状態になる。

## 重要な設計判断（先に決めておくべきこと）

実装に入る前にここだけは決めておく。後から変えると作り直しになる箇所。

### 1. 資金調達方式は2種類とも用意する

- **All-in（実行確定型）**: 目標未達でも集まった分を受け取れる。プロジェクトは必ず実行。
- **All-or-Nothing（目標達成型）**: 目標達成時のみ決済実行。未達なら1円も動かない。

自分たちの曲プロジェクトは **All-in で始めるのが楽**（決済が即時完結し、実装が単純）。
ただし他人が出品するプラットフォームにする以上、All-or-Nothing も需要があるので DB とフローは最初から両対応で設計しておく。詳細は [06-stripe.md](docs/06-stripe.md)。

### 2. All-or-Nothing は「オーソリ保留」ではなく「カード保存 → 締切後に決済」

Stripe のオーソリ（与信確保）は**最大7日で失効**する。クラファンは30〜60日が普通なので、オーソリ方式は成立しない。
正解は **SetupIntent でカードを保存 → 締切時に達成していれば off_session で一括決済**。
この方式は締切時の決済失敗（残高不足・3DS 再認証要求・カード期限切れ）が必ず一定割合発生するので、**失敗時のリトライとメール督促のフローが必須**。これを見落とすと「達成したのに入金が合わない」事故になる。

### 3. 金額は必ず整数（円）で持つ

`Int` で統一。`Float` / `Decimal` は使わない。日本円は最小単位が1円なのでこれで問題ない。将来の多通貨対応は捨てる。

### 4. 出品は「審査あり」で始める

誰でも出品できるプラットフォームにするが、**公開前に運営（自分たち）が承認する**フローを最初から入れる。
理由: 詐欺案件・権利侵害・公序良俗違反が1件でも通ると Stripe アカウントごと止まるリスクがある。承認は最初は手動で十分。

### 5. お金の動きは最初から複式簿記の台帳に記帳する

`currentAmount` のような残高だけ持っていると、「Stripe と ¥1,240 ズレている。どこで？」に答えられない。
**後から台帳を足しても過去分を再構成できない**ので、最初から入れる。詳細は [11-payment-hardening.md](docs/11-payment-hardening.md)。

### 6. 支援者への送金は「決済と同時」ではなく「募集終了+7日」

destination charge のデフォルト（決済と同時に出品者へ送金）は、返金・チャージバックの原資が消えるので危険。
送金を遅延させると**資金リスク対策とコスト削減が同じ実装で両立する**。

### 7. ポイントは「何とも交換できない」ものにする

リポスト・紹介でポイントが貯まる仕組みを入れるが、**換金・支援充当・交換を一切できなくする。**
交換できた瞬間に景品表示法の景品規制が付いてくる。表示・称号・ランキングだけなら議論が発生しない。
さらに**紹介報酬は1段階のみ**（多段階は特商法の連鎖販売取引に該当しうる）、
**シェアテンプレートに `#PR` を必ず入れる**（ステマ規制）。詳細は [12-points-gamification.md](docs/12-points-gamification.md)。

### 8. 手数料率を先に決める

参考: CAMPFIRE は 17%（プラットフォーム 12% + 決済 5%）。
提案: **プラットフォーム手数料 10% + Stripe 決済手数料 3.6%** ＝ 実質 13.6% 相当。
立ち上げ期は「手数料 8%」など安さを打ち出すのも手。数値は [06-stripe.md](docs/06-stripe.md) の計算式に定数として入れる。

## 名前について

`FUNDBEAT` は仮。音楽発オリジンが伝わる名前の候補：

- **FUNDBEAT** — fund + beat。分かりやすい。
- **RECOUP** — 音楽業界用語（原盤費の回収）。玄人向け。
- **ぷれす（PRESS）** — レコードのプレス。和名で親しみやすい。
- **AMPLIFY / AMP** — 増幅。支援で音が大きくなるイメージ。

決まったら `docs/` 内の `FUNDBEAT` を一括置換すれば済むようにしてある。
**ドメインと商標の空き確認は名前決定前に必ずやること。**
